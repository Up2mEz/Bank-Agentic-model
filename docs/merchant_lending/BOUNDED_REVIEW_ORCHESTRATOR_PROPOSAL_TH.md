# แบบเสนอ: Orchestrator ตรวจหลักฐานและส่งเจ้าหน้าที่ตัดสิน

สถานะ: **ข้อเสนอที่อิงผลทดสอบ ยังไม่ได้ติดตั้งใน product** อ้างอิง [audit 18 เคสและ Typhoon จริง 2 เคส](FINANCIAL_SCENARIO_AUDIT_20261023_TH.md) ไม่มีการกำหนดเกณฑ์อนุมัติใหม่แทนทีมเครดิต

## แนวทางที่แนะนำ

ใช้ Controller เดิมเป็น Orchestrator ของหนึ่ง case/review แล้วเพิ่ม issue queue และเครื่องมือตรวจเฉพาะเรื่อง ไม่จำเป็นต้องมี agent อิสระหลายตัวทำงานทุกเคส ใน sandbox นี้ใช้ Python/Go ที่มีอยู่ได้ ไม่ต้องเพิ่ม AWS เพื่อพิสูจน์พฤติกรรมเหล่านี้

ลำดับงาน:

1. รับจาก Android: คำขอ/ความยินยอม/เอกสาร ผูกเจ้าของและ version กับ onboarding จริง
2. ตรวจพื้นฐานทุกเคส: อ่าน OCR, schema, ยอดเปิด–ปิด, วันที่/เดือน, เจ้าของบัญชี, รายการซ้ำ, ประเภทที่ยังไม่ทราบ และเทียบกับคำแจ้ง
3. รวมทุกประเด็นเป็น issue queue ก่อนเลือกทางเดิน เพื่อไม่ให้ปัญหาหนึ่งซ่อนอีกปัญหา
4. กฎที่ทีมเครดิตกำหนดเลือกเครื่องมือหรือ specialist เพิ่มเฉพาะ issue; ส่งบริบทและ refs เฉพาะส่วนที่ต้องใช้
5. หากข้อมูลสำคัญยังพิสูจน์ไม่ได้ ให้ WAIT_CUSTOMER หรือ EXCEPTION_REVIEW พร้อมคำถามและหลักฐานที่ขอ แล้วจบรอบ
6. เมื่อข้อมูลที่จำเป็นพร้อม เครื่องมือคำนวณกระแสเงินสด/ภาระชำระ/ข้อเสนอวงเงิน แล้วสร้าง packet ให้เจ้าหน้าที่
7. เจ้าหน้าที่ตรวจเหตุผลและเอกสารจริง ตัดสินด้วย version ล่าสุด; ผลกลับไปที่ Android

ไม่ต้องเรียก LLM ในขั้นที่มีคำสั่งเครื่องมือให้เลือกเพียงคำสั่งเดียว การทดลอง C01/C06 ใช้ LLM 8 calls ต่อเคส แต่ส่วนใหญ่ถูกกำหนดทางเดินโดย Controller อยู่แล้ว จึงมีโอกาสลด calls โดยคง checks เดิมไว้ ส่วน LLM ใช้กับการอธิบายความหมายที่ไม่ชัด ร่างคำถาม และสรุปหลักฐานที่มี refs

## ใช้สิ่งที่มีอยู่และเพิ่มเฉพาะส่วนที่ขาด

| บทบาท | ของเดิม | สิ่งที่เสนอเพิ่ม |
|---|---|---|
| Orchestrator | `Controller.run`, `LendingController.allowed` | issue queue, routing ตาม policy version, รวมคำถามก่อนหยุด |
| OCR | `document_extract → TyphoonOCR` รุ่น `typhoon-ocr` | ตรวจคุณภาพและความครบของผล OCR; อ่านได้ไม่ได้แปลว่าเอกสารแท้ |
| ตรวจ statement | `statement_read → verify_statements` | account inventory, transaction identity/counterparty, cross-account matching |
| ตรวจที่มารายได้ | keyword classifier | ประเภทเงินเข้าและ recurrence พร้อมหลักฐาน/สถานะ UNKNOWN; specialist ช่วยเสนอคำอธิบาย |
| คำนวณ | `financial_calculate` ใช้ Decimal | monthly residual/low-month liquidity/ค่างวดใหม่ และภาระที่พิสูจน์ได้หรือยังต้องถาม |
| กฎเครดิต | `policy_evaluate` เดโม 4 rules | แยกข้อมูลไม่พร้อมออกจากกำลังชำระ; ประเด็นสำคัญที่ unresolved ห้ามกลบด้วยคะแนนรวม |
| ข้อมูลจากธนาคาร | `onboarding_read` | อ่านสินเชื่อเดิม/ประวัติชำระ/วงเงินรวมเมื่อทำ reassessment ตามสิทธิ์ |
| ส่งคน | `review_build_packet`, staff `Reviews` | issue/question ledger, ก่อน–หลังของข้อมูลและข้อเสนอวงเงิน; คำตัดสินยังเป็นของคน |

## กฎเลือกตรวจเพิ่มเติม

| Trigger | งานที่เลือก | ผลที่ต้องได้ก่อนจบรอบ |
|---|---|---|
| รายการเหมือนโอนข้ามบัญชีตนเอง | transfer/provenance check | คู่รายการและเจ้าของบัญชีที่พิสูจน์ได้; เท่ากัน/วันเดียวกันอย่างเดียวไม่ใช่หลักฐานเพียงพอ |
| เงินก้อนผิดจากรูปแบบเดิม | source/recurrence check | ขายสินค้า/เงินยืม/ทุน/ขายทรัพย์สิน/UNKNOWN; ขอ invoice/สัญญา/statement ต้นทางตามกรณี |
| รายรับแกว่งหรือเงินเหลือติดลบ | monthly liquidity check | ตารางแต่ละเดือน ช่วงเงินขาดมือ สมมติฐานฤดูกาลและแผนชำระที่ยังต้องตรวจ |
| เงินออกซ้ำสูงกว่าคำแจ้ง | expense clarification | รายการที่เกี่ยวข้องและคำถามว่าเป็นต้นทุน ค่าเลี้ยงดู ค่างวด หรืออย่างอื่น ไม่สรุปเป็นหนี้จากรูปแบบอย่างเดียว |
| คำแจ้งไม่ตรงข้อมูล | declaration reconciliation | expected/observed/difference พร้อม refs และคำถามเป็นกลาง ไม่มีข้อกล่าวหาโกหก |
| เดือน/บัญชี/เงินสดไม่ครอบคลุม | evidence completeness | สิ่งที่ทราบ/ยังพิสูจน์ไม่ได้/รายการเอกสารที่ขอ ไม่มีคะแนนมั่นใจสูงแทนหลักฐาน |

ตัวอย่างคำถามที่ใช้ติดตามได้:

- “วันที่ 22 ก.ค. รับ 900,000 บาทตามรายการนี้ เป็นเงินจากกิจกรรมใด เกิดครั้งเดียวหรือเกิดซ้ำ กรุณาแนบหลักฐานที่มา”
- “พบเงินออกให้ FAMILY-X เดือนละ 20,000 บาท 6 รายการ เป็นค่าใช้จ่ายประเภทใด และรวมอยู่ในยอดที่แจ้งแล้วหรือยัง”
- “คุณแจ้งว่าใช้ OWN-A และ OWN-B ขณะนี้มี statement เฉพาะ OWN-A กรุณาแนบ OWN-B ครบช่วงที่ระบุ”
- “ยอดขายที่แจ้ง 300,000 บาท/เดือน ต่างจากยอดเข้าที่ระบุเป็นยอดขาย 200,000 บาท ส่วนต่างเป็นเงินสด อีกบัญชี หรือรายการประเภทอื่น”

## โครงสร้างประเด็นและการหยุดงาน

แต่ละ issue ควรมี `issue_id`, `code`, `severity`, `status`, `case_version`, `evidence_hash`, `refs`, `expected`, `observed`, `unknowns`, `question`, `requested_evidence`, `owner`, `resolution` โดยแยกสถานะพิสูจน์ไม่ได้ออกจากข้อมูลขัดแย้ง ไม่ตีความ UNKNOWN เป็น false หรือศูนย์

ประมวลผล specialist หนึ่งครั้งต่อ `(case_version, issue_code, evidence_hash)` ในรอบเดียว; retry เฉพาะข้อผิดพลาดชั่วคราวตามงบและ deadline รวม ผลลัพธ์ต้องเป็น schema ที่กำหนด และ refs ต้องชี้กลับข้อมูลที่ส่งให้จริง หากยังตอบไม่ได้ให้ `UNRESOLVED` พร้อมคำถาม ไม่เรียกตัวเองวนเพื่อเพิ่มความมั่นใจ

งบเดิมมี 12 turns/600 วินาทีต่อ active run และไม่มี currency cost cap ที่ตั้งค่าแล้ว ควรแยกจำนวน specialist calls จากขั้นเครื่องมือที่ไม่ใช้ LLM และบังคับ deadline ส่งต่อถึงแต่ละเครื่องมือด้วย การตรวจเวลาระหว่าง turns อย่างเดียวไม่ใช่ hard wall-clock interruption

คงชื่อสถานะที่มีอยู่เพื่อลดการเปลี่ยน contract:

- `WAIT_CUSTOMER`: ต้องได้ข้อมูลจากลูกค้าเพิ่ม
- `EXCEPTION_REVIEW`: ต้องให้คนช่วยตีความ/ตรวจข้อขัดแย้ง พร้อมคำถามค้างทั้งหมด
- `TECHNICAL_REVIEW`: OCR/API/tool ล้มเหลว ไม่มีข้อสรุปทางเครดิตจากความล้มเหลวนั้น
- `REVIEW_READY`: packet พร้อมให้เจ้าหน้าที่ตัดสิน อาจเสนอ decline ได้หากข้อมูลครบแต่กำลังชำระไม่พอ
- `APPROVED`/`DECLINED`: เกิดจาก reviewer endpoint เท่านั้น ไม่อยู่ใน tools ที่ LLM เรียกได้

เพื่อป้องกัน C14 ต้องรวบรวม “ขาดกรกฎาคม” และ “เงินก้อนไม่ทราบที่มา” ลง packet/คำถามพร้อมกันก่อน route แม้สุดท้ายเลือก EXCEPTION_REVIEW

## วงเงินเริ่มต้นและการทบทวน

ให้ทีมเครดิตกำหนดเพดานเริ่มต้น เช่น 5,000 หรือ 10,000 บาท พร้อมผลิตภัณฑ์ ดอกเบี้ย ระยะเวลา หลักฐานขั้นต่ำ วิธีนับรายรับ/รายจ่าย และข้อยกเว้น วงเงินเสนอควรไม่เกินค่าต่ำสุดของคำขอ กำลังชำระ เพดาน tier และ headroom รวมที่คำนวณจากภาระปัจจุบัน เงื่อนไขข้อมูลสำคัญต้องครบก่อนใช้สูตร

เงินเข้าไม่เท่ากับรายได้; ไม่เห็นรายการหนี้ไม่ใช่ข้อพิสูจน์ว่าไม่มีหนี้ และมีหลักฐานเพิ่มไม่จำเป็นต้องเพิ่มวงเงิน ข้อมูลใหม่อาจยืนยันรายได้เพิ่ม พบภาระเพิ่ม หรือทำให้วงเงินที่เหมาะสมลดลงได้

เมื่อมีคำขอทบทวน/หลักฐานใหม่/ประวัติชำระถึงเงื่อนไขที่ทีมกำหนด ให้สร้าง review ใหม่ที่เชื่อม `previous_review_id` และ `facility_id` แช่ผลตัดสินเดิมไว้ เปรียบเทียบสิ่งที่เปลี่ยน ตรวจช่วงข้อมูลล่าสุดและ onboarding/consent แล้วประเมินใหม่ ส่งคนตัดสินสุดท้ายอีกครั้ง

ในระบบปัจจุบัน revise ทำได้ก่อน final decision ส่วนเคส APPROVED/DECLINED แก้ไม่ได้ จึงต้องเพิ่มการเชื่อม “รอบทบทวนใหม่” กับสินเชื่อเดิม ไม่เปิดแก้คำตัดสินเก่า ระบุให้ชัดว่า 10,000 บาทคือวงเงินรวมใหม่หรือวงเงินเพิ่ม และอย่าลืมหนี้เดิมหรือหักภาระเดิมซ้ำ

## ลำดับงานถัดไปที่ตรวจรับได้

1. เพิ่ม structured declarations/account inventory/cash-sales evidence โดยออก contract revision ร่วม Android/Go/Python; ครอบคลุม C09/C11/C12
2. เพิ่ม provenance/recurrence และ cross-account checks ให้ C04/C06 ไม่กลายเป็น recurring R จาก keyword
3. รวม issue/question ledger และเพิ่ม liquidity route; ทำ C05/C07/C08/C14 ให้ครบพฤติกรรมที่ต้องการ
4. เพิ่ม policy สำหรับเพดานเริ่มต้นและ linked reassessment เมื่อมีค่าจากทีมเครดิต แล้วใช้ชุดทดสอบเดิมตรวจย้อนกลับ พร้อมเคสข้อมูลใหม่ทำให้ข้อเสนอเพิ่ม/คง/ลด

การทำครบข้อเหล่านี้จึงเป็น bounded agentic review ตามแนวทางผู้ใช้ ปัจจุบันมีแกน Orchestrator และ human gate แล้ว แต่ยังไม่มี specialist routing และ workflow เพิ่มวงเงินที่ครบดังแบบนี้
