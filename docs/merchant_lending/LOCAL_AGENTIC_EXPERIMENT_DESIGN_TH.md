# Local agentic experiment — 23 ตุลาคม 2026

ผู้ใช้ให้ทดลอง local แก้เคสที่ไม่ผ่าน หลังแก้ context แล้วจึงเพิ่มเทคนิค agentic; ไม่บังคับใช้ LangGraph รอบนี้เป็น spike ที่ได้รับอนุญาต ใช้ controller/calculator/parser เดิมร่วมกับส่วนทดลองใหม่ ไม่เปลี่ยน HTTP/Android contract หรือสูตรเครดิต

## สมมติฐานและการเปรียบเทียบ

1. Context ที่เพิ่ม rows/issues/refs ทำให้โมเดลเห็นปัญหา แต่ tool schema เดิมที่รับแค่ reason ยังแก้การจัดหมวดและ route ไม่ได้ ตรวจแบบ context-only โดยคง tools/controller เดิม
2. Agent ต้องเลือก evidence tools ตาม observation แล้วส่ง structured findings ให้ validator จึงทำให้ข้อสงสัยมีผลต่อการตรวจเพิ่มและ packet ได้
3. การตรวจยอด คู่โอน กระแสเงินสดและการกั้นข้อมูลไม่พอเป็นงานโค้ด ผลที่ดีขึ้นจากงานเหล่านี้ไม่อ้างว่าเป็นความฉลาดของ LLM

## ส่วนที่เพิ่ม

- Context ที่ปิดชื่อ/ข้อมูลติดต่อแต่คงข้อความธุรกรรม จำนวนเงิน เดือน refs และประเด็นไว้ ไม่มี scenario ID หรือ oracle ส่งเข้าโมเดล
- หนึ่ง agent loop: observe → เลือก tool/arguments → ตรวจ schema/สิทธิ์/refs → tool result → เลือกขั้นถัดไป → ส่งคน
- Tools: `read_transactions`, `match_transfers`, `compare_declarations`, `inspect_cashflow`, `propose_findings`, `flag_transactions`, `finish_review` เป็น interface ภายในส่วนทดลอง ไม่ใช่ endpoint ใหม่
- `flag_transactions` ให้ agent เปิดประเด็นใหม่จากรายการที่อ่านแล้วได้ แม้กฎเริ่มต้นไม่ได้เตือน รายการถูกพักเพื่อขอหลักฐานและต้องคำนวณ cashflow ใหม่ ไม่มีสิทธิ์เพิ่มรายได้เอง
- Cross-account matching ต้องมีสองขา เจ้าของตามเอกสารสอดคล้อง ทิศทาง/จำนวน/วันและบัญชีคู่โอนตรงกัน การจับคู่จาก OCR ยังไม่รับรองเอกสารแท้
- เงินเข้าที่มีที่มาใหม่/ครั้งเดียวหรือเป็นโอนยังไม่ชัด แยกพักจาก recurring revenue ก่อน โมเดลเสนอชนิดพร้อม quote/refs ได้ แต่ไม่มีสิทธิ์ยืนยันรายได้ UNKNOWN เป็นยอดขายเอง
- คำแจ้งที่โมเดลสกัดต้องมี quote ตรงกับข้อความลูกค้า และตัวเลข/บัญชีตรงกับ quote คำแจ้งไม่แทนหลักฐานและไม่เพิ่มยอดรายได้
- ตรวจความครอบคลุมของคำแจ้งด้วย: การส่งกลับเพียงบาง claim ต้องไม่เท่ากับตรวจครบ ส่วนของข้อความที่ยังไม่ได้จำแนกคงเป็นคำถามที่กั้นการคำนวณ ไม่เชื่อ boolean ว่า complete จาก LLM เอง
- เงินขาดมือรายเดือนก่อให้เกิดประเด็นส่งคน โดยคงผลคะแนน/สูตรเดิมไว้ให้เห็นว่าทำไมคะแนนรวมอย่างเดียวไม่เพียงพอ
- รวม issues ก่อนเลือก WAIT_CUSTOMER / EXCEPTION_REVIEW; ข้อมูลไม่ครบไม่คำนวณวงเงิน และไม่มอง API failure เป็นเครดิตไม่ดี
- จำกัดจำนวน model calls/เวลาต่อรอบ; ผลซ้ำมี receipt; ไม่มีหลักฐานใหม่ไม่วนเพิ่มความมั่นใจ ไม่มี tool อนุมัติหรือจ่ายเงิน
- หลัง live รอบแรกพบการเรียกอ่าน/จับคู่ซ้ำ เพิ่ม progress, refs ที่อ่านแล้ว, งบที่เหลือ และเลือกเปิดเครื่องมือตามสถานะ พร้อมประวัติ assistant/tool ที่ผูกกับผลจริง เก็บรอบล้มเหลวไว้เพื่อไม่ปนกับผลรุ่นแก้
- แยก source ของคำแจ้งลูกค้าออกจาก memo และค่าคำนวณอย่างชัดเจน; ข้อความที่ถูกปิดชื่อ/แทนด้วย account alias ไม่ใช่หลักฐานว่าข้อมูลขัดแย้ง
- หลัง live V3 พบทั้งคำตอบแบบ prose ไม่มี tool call และ ref ผิด enum เพิ่มการส่ง validation feedback ให้แก้ได้เพียงหนึ่งครั้งในเพดานแปดครั้งเดิม ไม่ execute คำตอบที่ถูกปฏิเสธ และไม่แก้ JSON หรือเดา tool แทนโมเดล
- ขั้นคำนวณเปิดเมื่อ audit คำแจ้งและตรวจ source issue ที่ต้องตรวจแล้ว จากนั้นเปิดเฉพาะ `finish_review` เพื่อส่ง snapshot พร้อมคำถามค้าง การคำนวณจึงเป็นจุดจบของการสืบค้นรอบนี้; หลักฐานใหม่ต้องเริ่ม review รุ่นใหม่ ไม่วนเปิดประเด็นหลังคำนวณไปเรื่อย ๆ
- ประวัติ native tool เก็บ observation จริงครบหนึ่งชุด; context ล่าสุดไม่ส่ง observation เดียวกันซ้ำ แต่ยังเก็บ validation feedback ที่ไม่มี native call คู่กันไว้ ห้ามเปลี่ยน legacy context-only ablation
- ผลเสนอจัดหมวดใช้ได้เฉพาะแถวที่อ่านและอ้างข้อความจริง แถวอื่นในกลุ่มยังไม่ถูกยืนยัน ข้อความส่งต่อใน packet เป็น template จากระบบ ส่วนข้อความโมเดลใน trace เป็นข้อมูลตรวจสอบ ไม่ใช่คำตัดสิน

## การแยกจากบริการที่เปิดอยู่

เพิ่มโมดูลและ runner ใหม่ อ่าน immutable audit snapshot/เอกสารด้วย SQLite read-only แล้วเขียนผลลง `outputs/lending-agentic-local-20261023/` เท่านั้น ไม่แก้ frozen source, fixtures/oracle เดิม, policy หรือ DB/ports/emulator ของเธรดอื่น ผลทดลองติดป้ายไม่ใช่ packet สำหรับ reviewer endpoint

OCR ใช้ข้อความที่เก็บไว้เพื่อแยกการทดสอบ reasoning ออกจาก extraction; เมื่อใช้ Typhoon จริง ระบุว่า live LLM + replayed OCR ไม่อ้างว่ารัน OCR ใหม่ KYC/onboarding ยังคง mock เช่น audit เดิม

## เกณฑ์ตรวจรับ

- 18 oracle เดิมยังคงเดิม เสริม assertions ที่เจาะจงกว่าการมีข้อความ feedback ทั่วไป: C09 ต้องชี้ 300000/200000 และ 10000/145000; C11 ต้องขอ OWN-B; C12 ต้องระบุเงินสด 50000 ที่ยังไม่มีหลักฐาน
- C04 มีคู่โอนจริงและไม่เพิ่มยอดขาย; C06 มี asset-sale interpretation ที่อ้างข้อความจริง; C07 มีเดือนขาดมือและไม่ถูกคะแนน 75 กลบ; C14 เก็บทั้งเดือนหายและเงินก้อน
- adversarial tests: refs ผิด/ข้ามเคส, quote ไม่ตรง, พยายาม promote UNKNOWN เป็นรายได้, ยอดเท่ากันแต่ไม่มีคู่บัญชี, unknown debt, consent false, final case และ budget/duplicate action
- เทียบ baseline / context-only / agentic โดยไม่เปลี่ยนโมเดลและสูตรพร้อมกัน เก็บคำสั่งเครื่องมือ ผลที่ได้รับ เหตุผลสั้น และการปฏิเสธ action; ไม่ต้องบันทึก chain of thought
- การผ่านชุดสังเคราะห์ไม่ใช่ความแม่นยำของสินเชื่อจริง และไม่ได้พิสูจน์ durable multi-worker deployment หรือ workflow เพิ่มวงเงินจากการชำระจริง

## เคสเสริมก่อนเรียกโมเดลจริง

เขียนเกณฑ์ไว้ก่อนรัน โดยไม่มี scenario ID/expected answer ส่งเข้าโมเดล และไม่เปลี่ยน oracle 18 เคสเดิม:

- H01: เงินเข้าทุกเดือนมี memo ว่า `shop sales - old equipment disposal proceeds` กฎรายรับครั้งเดียวไม่เตือน ต้องดูว่า agent อ่านแล้วเปิดประเด็นและพักรายรับเองได้หรือไม่ ไม่คาดหวังการยืนยันชนิดจาก memo อย่างเดียว
- H02: เงินเข้าทุกเดือนเขียนว่า `sales transfer from outside account` แต่ไม่มี statement ต้นทาง ต้องไม่ยืนยันเป็นรายได้หรือจับคู่จากยอดเท่ากันอย่างเดียว
- H03: เปลี่ยนคำแจ้งเป็นยอดขาย 275,000 และต้นทุน 25,000 บาทต่อเดือน เทียบ statement 200,000 / 145,000 ต้องสร้างสอง comparison ที่อ้างข้อความจริง ไม่จำตัวเลข C09
- H04: เดือนหนึ่งมีเงินเหลือ 8,000 บาทก่อนสำรองและค่างวดใหม่ แม้เป็นบวก ต้องชี้เดือนที่ไม่พอหลังสำรองและผ่อนตามข้อเสนอเดิม ไม่อาศัย median อย่างเดียว

ชุดนี้เป็น held-out ต่อ 18 fixture เดิม แต่สร้างโดยผู้พัฒนาในรอบนี้ จึงเป็นการตรวจพฤติกรรมเพิ่มเติม ไม่ใช่ชุดประเมินภายนอกหรือข้อมูลลูกค้าจริง

LangGraph จะพิจารณาอีกครั้งเมื่อจำเป็นต้องทำ checkpoint/restart หลาย worker; loop ใน spike ต้องแสดงประโยชน์ของการใช้ agent ก่อน ไม่เพิ่ม framework เพื่อเปลี่ยนชื่อ workflow อย่างเดียว
