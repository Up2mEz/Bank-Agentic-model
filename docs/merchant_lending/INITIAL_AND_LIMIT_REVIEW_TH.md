# การขอสินเชื่อครั้งแรกและการทบทวนวงเงิน

วันที่ตรวจ 23 ตุลาคม 2026 — ตรวจ source และ saved receipts แบบอ่านอย่างเดียว พร้อมข้อเสนอ workflow ยังไม่ได้เพิ่ม repayment API, behavioral score หรือ workflow เพิ่มวงเงินจริง และไม่ได้เรียก LLM/OCR/ธนาคารใหม่

## สิ่งที่มีจริงในตอนนี้

เส้นทางแอปใช้ `LendingController` กับ planner ตามการตั้งค่า: รับคำขอ → อ่าน onboarding → OCR → ตรวจตัวตนและ statement → คำนวณ → ประเมินกฎ → แฟ้มเจ้าหน้าที่ → ผลตัดสินของคน เส้นทางนี้อยู่ใน [server.py](../../src/merchant_sandbox/server.py) และ [lending.py](../../src/merchant_sandbox/lending.py)

ส่วน native tool agent ใน `agentic_review.py` และรายงาน 4 ส่วนเป็น **local experiment แยกต่างหาก** ยังไม่ได้เชื่อมเข้าเส้นทางแอปข้างต้น จึงยังใช้ผลทดลองใหม่รับรองพฤติกรรมแอปทั้งระบบไม่ได้

คำขอปัจจุบันเหมาะกับ **พิจารณาวงเงินตั้งต้น และส่งข้อมูลเพิ่มเติมในคำขอเดียวกัน** ยังไม่มี `facility_id`, ประเภทการขอเพิ่มวงเงิน, repayment history และยอด exposure จริงเข้ามาใน contract ของ Agent การเก็บประวัติ case/version มีแล้ว แต่ไม่ใช่การติดตามการชำระของสินเชื่อที่ปล่อยจริง

fixture การเงินยังเป็นเบิกเต็มครั้งเดียว 6 งวด งวดละ 30 วัน และ `revolving_redraws_validated=false` ค่า headroom เป็นค่าคงที่เดโม 50,000 บาทใน [config](demo_parameters.json) ไม่ใช่วงเงินคงเหลือที่ดึงจาก Loan Core

## ตอนยื่นครั้งแรกตรวจอะไร

1. **ตัวบุคคลและร้าน:** เจ้าของคำขอ/บัญชี, phone, KYC session ปัจจุบัน, wallet, KYB และความยินยอม ตรวจสถานะจาก backend; OCR ชื่อตรงไม่พิสูจน์บุคคลจริงหรือเอกสารแท้
2. **ความครบของหลักฐาน:** บัญชีที่แจ้งทั้งหมด, ช่วงเวลา, แถวซ้ำ, ยอดต่อเนื่อง, ข้อขัดแย้งและรายการที่ยังไม่ทราบที่มา การตรวจพื้นฐานมีแล้ว แต่พบช่องว่างตามผลทดลอง
3. **ที่มาของเงิน:** แยกยอดขายที่มีหลักฐาน, เงินกู้/ทุน/โอนตนเอง, ภาระจ่าย และ UNKNOWN พร้อมคำถาม อย่าใช้เงินเข้าทั้งหมดเป็นรายได้
4. **กำลังชำระ:** รายรับหลังต้นทุน ค่าใช้จ่ายจำเป็น หนี้เดิม เงินสำรอง และภาระใหม่; ดูเดือนขาดมือและเงื่อนไขรายได้ลดด้วย
5. **กฎและข้อเสนอ:** ใช้ product/terms/caps ที่ระบุ version; วงเงินที่คำนวณได้เป็นข้อเสนอ ส่งคนพร้อมข้อจำกัด

ใน [core.py:492](../../src/merchant_sandbox/core.py#L492) คะแนนปัจจุบันเป็น `demo_policy_score` 25 คะแนนต่อกฎ รวม 100:

| กฎเดโม | ตรวจอะไร |
|---|---|
| S1 | เงินเหลือก่อนหนี้ใหม่เป็นบวกอย่างน้อย 5 ใน 6 เดือน |
| S2 | มัธยฐานเงินเหลือเป็นบวก |
| S3 | ความผันผวนรายรับแบบ population CV ไม่เกิน 0.50 |
| S4 | มัธยฐานรายรับ 3 เดือนล่าสุดไม่น้อยกว่า 80% ของมัธยฐาน 6 เดือน |

เกณฑ์เหล่านี้เป็นค่าทดลอง ไม่ใช่นโยบายธนาคารที่ validate หรือแบบจำลองโอกาสผิดนัด และยังมีปัญหาเชิงนโยบาย: ผ่าน 3 ข้อได้ 75 แม้ข้อเงินเหลือรายเดือนตก จึงต้องคง liquidity/uncertainty gates แยกจากคะแนนรวม ข้อมูลมากขึ้นไม่ใช่คะแนนดีขึ้นอัตโนมัติ

## ข้อเสนอ: แบ่ง workflow ตามวงจรสินเชื่อ

**FIRST_APPLICATION:** ตัวตน/ร้านและสิทธิ์ → ตรวจหลักฐาน → Agent เลือกตรวจประเด็น → calculator/policy → แฟ้มเจ้าหน้าที่ การขอครั้งแรกกับเราไม่ได้แปลว่าไม่มีหนี้ที่อื่น

**SERVICING_REVIEW:** หลังมีสินเชื่อจริง จึงอ่าน schedule + settled allocations + balances/holds จาก Loan Core เพื่อคำนวณประวัติชำระ ไม่ตีความจากยอดเงินออกใน statement อย่างเดียว ข้อมูลผิดปกติส่งคนตรวจ/ช่วยเหลือ ไม่สร้างคำสั่งเปลี่ยนวงเงินจาก LLM

**LIMIT_INCREASE:** ลูกค้าขอเพิ่ม → สร้าง review ใหม่ผูกสินเชื่อ/วงเงินเดิม → ตรวจสถานะและข้อมูลล่าสุด → เทียบกับ snapshot รอบก่อน → อ่านประวัติชำระและภาระทั้งหมด → คำนวณกำลังชำระหลังเพิ่ม → ให้คนพิจารณา ไม่แก้ทับคำตัดสินเดิม และต้องตรวจ version/exposure อีกครั้งก่อนบันทึกผล

**HARDSHIP_REVIEW:** มีค้างชำระ/รายได้สะดุด → ตรวจความถูกต้องและสาเหตุ → ส่งทีมช่วยเหลือ/เจ้าหน้าที่ตามนโยบายที่อนุมัติ ไม่สรุปว่าควรเพิ่มวงเงินเพื่อจ่ายหนี้เดิมหรือปฏิเสธอัตโนมัติ

หลักประเมินภาระหนี้และเงินเหลือใช้ทั้งสินเชื่อใหม่และการเพิ่มวงเงินตามเอกสารแนบ 4 ของ [ประกาศ ธปท. 3/2568 หน้า 24 ของ PDF](https://www.bot.or.th/content/dam/bot/fipcs/documents/FPG/2568/ThaiPDF/25680030.pdf#page=24) การใช้งานจริงต้องผูกกับประเภทผู้ให้กู้/ผลิตภัณฑ์และข้อยกเว้นที่เกี่ยวข้อง ไม่ใช้ threshold ของเดโมแทนเกณฑ์กำกับ

## Context/evidence ที่ควรเพิ่มสำหรับรอบเพิ่มวงเงิน

| กลุ่มข้อมูล | แหล่งหลักฐาน | สิ่งที่ให้ tool คำนวณ/Agent ตรวจ |
|---|---|---|
| ข้อตกลงปัจจุบัน | Loan Core: facility/loan IDs, terms version, due schedule | งวดที่ครบกำหนดแล้ว จำนวนที่ต้องจ่าย วันที่มีผล cutoff/timezone/grace ตามสัญญา |
| ประวัติชำระ | Settled payment + allocation ledger | ครบตามกำหนดกี่งวดจากทั้งหมดกี่งวด, จ่ายบางส่วน, DPD ปัจจุบัน/สูงสุด, ความถี่และแนวโน้มช้า |
| การจ่ายเร็ว | วันที่ชำระมีผลและการตัดชำระจริง | ก่อนกำหนดครบงวดหรือเพียงจ่ายบางส่วน; โปะเงินต้นหรือชำระงวดอนาคตตามสัญญา; ที่มาเมื่อเป็นก้อนผิดปกติ |
| เงินต้น/วงเงิน/ภาระผูกพัน | ยอดคงเหลือ, ดอก/fee, holds, facilities อื่น | Exposure จริงและ available credit; อย่าหักภาระสินเชื่อเดียวซ้ำทั้งจาก statement และ ledger |
| ธุรกิจปัจจุบัน | Statement ใหม่, POS/QR settlement, ใบเสร็จ/คำสั่งซื้อที่เกี่ยวข้อง | ยอดขายสุทธิหลังคืนเงิน, รายได้หาย/ฤดูกาล, เงินสำรองและทุนหมุนเวียน; reconciliation ป้องกันนับ POS/QR/statement ซ้ำ |
| หนี้/ภาระอื่นที่เปลี่ยน | คำแจ้งล่าสุด, ใบแจ้งหนี้/ตารางผ่อน, bureau เมื่อเข้าถึงได้โดยชอบ | หนี้เกิดใหม่ ภาระผ่อนทั้งหมด ข้อจำกัดข้อมูลที่ไม่เห็นนอกบัญชี |
| เป้าหมายขอเพิ่ม | คำขอลูกค้า + หลักฐานความต้องการ เช่น ใบสั่งซื้อ | ใช้ทำอะไร จำนวน/ช่วงเวลาที่ต้องใช้ และกระแสเงินสดรองรับภาระใหม่ |
| ปัญหาระบบ/ข้อโต้แย้ง | Settlement/reversal records, incident/correction IDs | Pending, duplicate, reversed หรือบันทึกช้าไม่ถูกตัดสินเป็นพฤติกรรมเสียโดยอัตโนมัติ |

ประวัติเครดิตมีทั้งการจ่ายตรงเวลาและค้างชำระ และมีสิทธิแก้ข้อมูลผิด; การดึงข้อมูลบูโรต้องมีสิทธิ์/ฐานการเปิดเผยที่เหมาะสม ไม่มี API บูโรจริงในงานนี้ [ธปท.: สิทธิของผู้มีประวัติในเครดิตบูโร](https://www.bot.or.th/th/satang-story/rights-responsibility/rights.html)

สำหรับ workflow ที่เสนอ **จ่ายเร็วไม่ควรได้โบนัสอัตโนมัติ**: ต้องรู้ว่าจ่ายครบเท่าไร ตัดเงินต้นจริงหรือไม่ และแหล่งเงินเป็นอะไร เงินขายทรัพย์สิน/เงินยืมครั้งเดียวไม่ได้พิสูจน์รายได้ประจำที่สูงขึ้น ส่วนจ่ายช้าต้องดูจำนวนวัน/ความถี่/สาเหตุและเวลามีผลจริง แยก late payment ออกจาก data/settlement error

ยังไม่มีงวดถึงกำหนด = `INSUFFICIENT_HISTORY` ไม่ใช่ on-time 100%; จ่ายหลายรายการเล็กในงวดเดียวไม่นับเป็นหลายงวดดี และส่วนที่จ่ายไม่ครบยังเป็นยอดค้างตามกติกาสัญญา Metric เหล่านี้คำนวณด้วยโค้ด ไม่ให้ LLM นับหรือแก้ ledger

ในผลิตภัณฑ์ **หมุนเวียน** การคืนเงินต้นอาจคืน available limit ตามเงื่อนไข แต่ไม่ได้เพิ่ม approved limit เช่น limit 10,000 ยอดใช้ 4,000 ไม่มี holds → available 6,000; ชำระเงินต้นสำเร็จ 1,000 → available 7,000 โดย approved limit ยัง 10,000 ตัวอย่างนี้ไม่ใช่พฤติกรรมที่ผ่านการทดสอบของ fixture เบิกเต็ม/ไม่เบิกซ้ำปัจจุบัน

## Orchestrator และ tools ที่เสนอ

ใช้ controller ตรวจพื้นฐานและเลือก route จากประเภทคำขอ/สถานะข้อมูล ให้ Agent เลือกตรวจเพิ่มเฉพาะประเด็นที่มีหลักฐานรองรับ; ตัวเลขหลักมาจาก deterministic tools ส่วนชื่อ tool ด้านล่างเป็น **ข้อเสนอใหม่**:

- `loan_servicing_read`: อ่าน terms, schedule, balances, payment allocations และ reversals ของลูกค้าที่ backend ผูกไว้
- `repayment_features`: คำนวณ matured installments, full-on-time ratio พร้อมตัวหาร, DPD, partial/early payments และคุณภาพข้อมูล
- `exposure_read` / `compare_review_snapshots`: ภาระผูกพันล่าสุดและสิ่งที่เปลี่ยนจากครั้งก่อน
- `request_evidence`: เพิ่มคำถามระดับบัญชี/เอกสาร/รายการโดยไม่เปลี่ยนการจัดหมวดหรือ ledger
- `quarantine_income`: กันรายรับเมื่อมีเหตุเฉพาะพร้อม refs แยกจากการตั้งคำถามทั่วไป
- `affordability_recalculate` / `policy_check`: ทบทวนภาระรวมหลังเพิ่มภายใต้ product terms ที่ทีมเครดิตกำหนด ไม่เพิ่มเพราะคะแนนประวัติสูงอย่างเดียว
- `review_packet`: คงรายงาน statement 4 ส่วน แล้วแนบประวัติชำระ, exposure, delta จากรอบก่อน, สาเหตุข้อเสนอ และคำถามค้าง

ส่ง context ก้อนเล็กที่มี `as_of`, window, coverage, source/version/ref, unknowns และ summary features; ให้ดึงรายละเอียดเพิ่มตาม refs เมื่อจำเป็น ไม่แนบประวัติทุกแถวใหม่ทุก turn และไม่ให้ชื่อบุคคล/ข้อมูลอ่อนไหวที่ไม่จำเป็นแก่ LLM

เมื่อยังพิสูจน์ไม่ได้ให้ขอข้อมูล/ส่งคนพร้อมสิ่งที่ค้าง; provider หรือแหล่งข้อมูลเสียให้แยก technical state; ตั้งเพดาน calls/time/token ต่อ review และไม่วนรอคำตอบที่ยังไม่มี ผู้ตัดสินวงเงินสุดท้ายยังเป็นเจ้าหน้าที่

## เคสที่ต้องเพิ่มก่อนบอกว่า workflow เพิ่มวงเงินผ่าน

รายการต่อไปนี้เป็น **NOT_RUN สำหรับ workflow ใหม่** ไม่ใช่ผลทดสอบที่ผ่านแล้ว:

| เคส | ผลที่คาดหวัง |
|---|---|
| ยังไม่มีงวดครบกำหนด | ประวัติไม่พอ ไม่สรุป on-time 100% |
| จ่ายก่อนนิดเดียว ที่เหลือจ่ายหลัง due | แสดง partial/late ตามยอดครบ ไม่จัดทั้งงวดเป็น early |
| จ่ายครบตรงเวลาสม่ำเสมอ แต่มีหนี้ใหม่หรือยอดขายลด | ตรวจ affordability ใหม่ ประวัติดีไม่ข้าม capacity gate |
| จ่ายจริงตรงเวลา แต่ posting ช้า/มี incident | ใช้เวลามีผลและหลักฐาน correction; ส่งคนตรวจข้อโต้แย้ง |
| โปะก้อนใหญ่จากขายทรัพย์สินหรือเงินกู้ใหม่ | ลดยอดต้นที่ชำระจริง แต่ไม่เพิ่ม recurring income อัตโนมัติ |
| Pending/reversed/duplicate payment | ไม่เพิ่มเครดิตการชำระซ้ำ; กระทบยอดและปรับ snapshot ตาม finality |
| ผ่อนหนี้เดิมพบทั้งใน statement และ ledger | ผูก loan/payment refs และหักภาระครั้งเดียว |
| ปรับตารางผ่อน/พักชำระอย่างเป็นทางการ | ใช้ schedule version ที่มีผล พร้อมรักษาประวัติเดิม |
| คืนเงินต้นในวงเงินหมุนเวียน | เปลี่ยน available ตาม terms โดย approved limit ไม่เปลี่ยน |
| Exposure/ข้อมูลสำคัญเปลี่ยนก่อนคนกดอนุมัติ | ผลเก่า stale ต้องตรวจใหม่ ไม่ใช้ snapshot เก่าเพิ่มวงเงิน |
| POS/QR refund หรือยอดซ้ำใน statement | นับยอดขายสุทธิและหักซ้ำไม่ได้ |
| ข้อมูลบริการหาย/หมดอายุ | UNKNOWN/NEED_MORE_INFO/TECHNICAL ไม่แต่งข้อมูลและไม่ auto-decline |

การกำหนดจำนวนงวดขั้นต่ำ น้ำหนัก early/late เกณฑ์ trigger และวงเงินแต่ละ tier เป็นงาน Credit/Product ต้องตกลงแยกต่างหาก รายงานนี้ไม่ได้กำหนด “จ่ายดี N งวดแล้วเพิ่มเป็น 10,000” เป็นนโยบายจริง
