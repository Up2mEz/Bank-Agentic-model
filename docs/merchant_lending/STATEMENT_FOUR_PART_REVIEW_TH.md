# รายงาน statement สำหรับเจ้าหน้าที่: 4 ส่วนตามหลักฐาน

ขอบเขตวันที่ 23 ตุลาคม 2026: งานทดลอง local ตามคำขอใหม่ของผู้ใช้ ไม่เปลี่ยน policy/สูตรสินเชื่อเดิม ไม่จำเป็นต้องจำแนกทุกรายการเป็นวัตถุดิบหรือส่วนตัว และไม่ตัดสินสินเชื่อแทนเจ้าหน้าที่

## รูปแบบที่ส่งให้เจ้าหน้าที่

1. **เงินรับที่มีหลักฐานว่าเป็นยอดขาย** — จำนวน วันที่ refs ของรายการ และหลักฐานประกอบที่จับคู่ได้ พร้อมระดับการสนับสนุน เช่น ข้อมูล settlement ที่แอปส่งมาหรือรายการสั่งซื้อที่จับคู่สำเร็จ ข้อความว่า sales เพียงอย่างเดียวไม่ยืนยันยอดขาย
2. **เงินเข้าที่ไม่ใช่ยอดขาย** — เงินกู้ เติมทุน โอนตนเอง ขายทรัพย์สิน และอื่น ๆ โดยแยกคำบรรยายใน statement ออกจากการตรวจคู่รายการ/หลักฐานภายนอกจริง ไม่บวกเป็นยอดขายประจำ
3. **ภาระจ่ายที่ระบุได้** — เช่น ค่าเช่า ค่าแรง ค่างวดที่มีหลักฐาน ไม่ถือว่าเงินออกประจำทุกก้อนคือหนี้ และไม่ถือว่าถอนเงินสดเท่ากับซื้อวัตถุดิบ
4. **รายการที่ต้องถามเพิ่ม** — ระบุ refs จำนวน สิ่งที่ยังพิสูจน์ไม่ได้ คำถามที่เป็นกลาง และเอกสารที่ขอเพิ่ม คง UNKNOWN เมื่อหลักฐานไม่พอ ไม่กล่าวหาหรือปฏิเสธสินเชื่ออัตโนมัติ

สี่ส่วนต้องไม่คิดยอดรายการเดียวซ้ำกัน การนำประเด็นหนึ่งไปถามเพิ่มต้องรักษารายการและยอดเดิมไว้ให้ตรวจย้อนกลับได้ ไม่ทิ้งรายการเพราะจัดหมวดไม่ได้ รายงานต้องมี `decision=null` และให้เจ้าหน้าที่ตรวจขั้นสุดท้าย

## หลักตรวจ 6 ประเด็น

| ประเด็น | ข้อมูล/การตรวจที่รายงานต้องแสดง | สิ่งที่ห้ามสรุปเกินหลักฐาน |
|---|---|---|
| เอกสารและบัญชี | เจ้าของบัญชีเทียบคำขอ บัญชีที่แจ้ง ช่วงเดือน ความต่อเนื่อง รายการซ้ำ ยอดต้น/ปลาย/ระหว่างแถว และข้อมูลที่อ่านไม่ได้ | ยอดตรงกันไม่พิสูจน์เอกสารแท้หรือ KYC สำเร็จ |
| แหล่งเงินเข้า | ช่องทาง/คู่รายการ/refs แยกยอดขาย เงินกู้ ทุน โอนตนเอง และขายทรัพย์สิน เทียบอาชีพ/ยอดที่แจ้ง | เงินเข้าไม่เท่ากับรายได้; คำบรรยายหรือ confidence ไม่แทนหลักฐาน |
| ความสม่ำเสมอ | หลายเดือน ค่าเฉลี่ย ต่ำสุด สูงสุด ความผันผวน เดือนที่ขาดข้อมูล/ไม่พบยอดที่พิสูจน์ได้ และแนวโน้มลด | ไม่มี supported sales ไม่เท่ากับพิสูจน์ว่ารายได้จริงเป็นศูนย์ |
| เงินออก/ภาระ | รายจ่ายที่จำแนกจากหลักฐานได้ ค่าใช้จ่ายจำเป็น/หนี้ที่ลูกค้าแจ้ง และส่วนที่ยังไม่ทราบ | บัญชีเดียวไม่พิสูจน์ว่าเห็นหนี้หรือเงินสดทั้งหมด |
| เงินเหลือ/สภาพคล่อง | ยอดเงินเข้า–ออกที่สังเกตได้แยกจากกำลังชำระ; ใช้ calculator เดิมเมื่อข้อมูลครบ ดูเดือนต่ำและสำรอง/ค่างวดตาม policy | ไม่เห็นเงินหมุนมากแล้วสรุปผ่อนไหว ไม่สร้างสูตร/วงเงินขึ้นเอง |
| รายการต้องอธิบาย | เงินก้อนใกล้ยื่นกู้ เงินเข้าแล้วออกเร็ว ความขัดแย้งพร้อมคำถามและ refs | รูปแบบผิดปกติเป็นเหตุสอบถาม ไม่ใช่หลักฐานทุจริต |

## แหล่งอ้างอิงที่ตรวจ

KBank อธิบาย dStatement ว่าเป็นการรับส่งข้อมูลเดินบัญชีดิจิทัลโดยตรงระหว่างสถาบันการเงินตามคำขอและความยินยอมของลูกค้า ช่องทางนี้เป็นคนละระดับ provenance กับการอัปโหลด PDF ที่ผ่าน OCR; **โปรเจกต์นี้ยังไม่ได้เชื่อม dStatement จริง** จึงไม่ติดป้าย bank-verified ให้ไฟล์ทดลอง [KBank dStatement](https://www.kasikornbank.com/th/promotion/pages/dstatement.aspx)

ธปท. ยกตัวอย่างหลักฐานผู้มีอาชีพอิสระเป็น statement บัญชีตนเองหรือกิจการย้อนหลังอย่างน้อย 6 เดือน และระบุว่าการเตรียมเอกสารต่างกันตามประเภทสินเชื่อ ดังนั้นระยะเวลาเป็นข้อกำหนดของผลิตภัณฑ์/ทีมเครดิต ไม่ตั้งเป็นกฎอนุมัติสากลจากบทความ [ธปท.: สิ่งที่ควรรู้เมื่อขอกู้เงิน](https://www.bot.or.th/th/satang-story/managing-debt/before-loan.html)

กรมส่งเสริมอุตสาหกรรมอธิบายการพิจารณาสินเชื่อธุรกิจโดยดูว่ากระแสเงินสดสุทธิเพียงพอผ่อนชำระหรือไม่ และการติดตามเงินขาดมือเป็นเหตุผลหนึ่งของการทำงบกระแสเงินสด ข้อความเหล่านี้เป็นหลักอธิบาย ไม่ใช่อัตราส่วน/threshold ที่รับรองสำหรับ policy ของเรา [หลักพิจารณาสินเชื่อ](https://www.dip.go.th/th/category/2020-05-22-19-38-58/2021-11-25-16-23-18), [งบกระแสเงินสดแบบง่าย](https://www.dip.go.th/th/news-detail/2020-05-22-19-38-58/2021-11-26-09-58-39)

## วิธีทดลองและ trace

เก็บผล Luna รอบก่อนแยกไว้ที่ `outputs/lending-openai-luna-20261023/` พร้อม frozen source snapshot ไม่ย้อนแก้คะแนน C11 FAIL หรือ C05/C08 PARTIAL

รอบใหม่ใช้ prompt contract `STAFF_FOUR_PART_V1` ร่วมกับเครื่องมือเดิม เพิ่มคำอธิบายชนิดค่าให้ชัด (หนึ่งบัญชีต่อ claim และเงินเป็นค่าตัวเลข) โดยไม่เปลี่ยน validator/financial policy รัน Typhoon ก่อน และเรียก Luna เฉพาะเคสที่ Typhoon ยังไม่ผ่าน แยกผลการตรวจโดย agent ออกจากการประกอบรายงานด้วยโค้ด ห้ามนับ postprocessor ว่าเป็นการค้นพบของ LLM

Trace เก็บ current context ที่ลบข้อมูลส่วนตัวแล้ว, tool/arguments ที่โมเดลเลือก, ผล validator/observation, refs และคำถามส่งต่อ รวม arguments ของ native call ที่ภายหลังถูก controller ปฏิเสธ จึงตามสาเหตุได้ดีกว่ารอบเดิม ไม่เก็บ private reasoning หรือ API key

การทดสอบนี้ใช้ข้อมูลจำลองและ OCR fixture/replay ไม่มีการรับรองเอกสารจริง ไม่มีการตัดสินสินเชื่อ และไม่แตะ runtime/DB/emulator ของเดโมที่ผู้ใช้กำลังทดลอง

## วิธีรันซ้ำโดยแยกจากบริการเดโม

รายงานยังเป็น module/CLI สำหรับการทดลอง ไม่ได้เพิ่ม endpoint หรือ reload เว็บเจ้าหน้าที่ที่กำลังใช้งานอยู่ ใช้ directory ใหม่ทุกครั้ง; script ปฏิเสธการเขียนทับผลเดิม

```powershell
. .\scripts\project-env.ps1
$env:PYTHONDONTWRITEBYTECODE = '1'
.\.venv\Scripts\python.exe -X utf8 tools/run_statement_review_experiment.py --provider typhoon --output outputs/statement-retest-typhoon --credential-file '<authorized-credential-file>'
.\.venv\Scripts\python.exe -X utf8 tools/run_statement_review_experiment.py --provider luna --typhoon-run outputs/statement-retest-typhoon --output outputs/statement-retest-luna --credential-file .env
```

เพิ่ม `--prepare-only` เพื่อสร้าง inputs/manifests โดยไม่โหลด credential หรือเรียก API; `--cases S01,S03` จำกัดเคส Typhoon ได้ ส่วน Luna อนุญาตเฉพาะ FAIL/PARTIAL ที่มีผล Typhoon ก่อนหน้าและ input/documents ตรงกัน

- ต่อเคส: ไม่เกิน 8 calls / 240 วินาที; HTTP timeout สูงสุด 45 วินาที และทิ้งผลที่กลับช้าเกิน deadline
- Typhoon: ไม่เกิน 56 calls สำหรับ 7 เคส, token guard 400,000 รวมทั้ง batch โดยกันพื้นที่คำขอถัดไปก่อนส่ง
- Luna: token guard 300,000, input budget 240,000 / output 32,000 และประมาณค่าใช้จ่ายสูงสุด **USD 0.04** สำหรับ batch ใหม่นี้ ตัวเลขเป็น reservation/estimate ไม่ใช่ยอดเงินคงเหลือในบัญชี
- ขาด usage หรือ provider/account error จะหยุด batch; เคสที่เหลือเป็น NOT_RUN ไม่ตีความเป็นสินเชื่อไม่ผ่าน

แต่ละเคสมี `staff-report.md`, `staff-report.json`, `case.json`, `model-contexts.json`, `public-choices.json`, `public-trace.json`, `provider-calls.json`, `evaluation-receipts.json` และ `result.json` มี `per-request-usage.csv` แยก token ต่อคำขอ ภายใน source-snapshot เก็บสำเนา source/test ที่ใช้จริง

`evaluation-receipts` ใช้ native receipt เดิมร่วมกับ arguments ที่ wrapper จับจากผลซึ่ง adapter ตรวจแล้ว เพื่อให้ OpenAI ซึ่ง receipt เดิมไม่เก็บ arguments สามารถตรวจเทียบ execution ได้ ไม่แก้ raw provider receipt และไม่นำ expected/oracle ส่งให้โมเดล

เกณฑ์คำถามของ evaluator มีข้อจำกัด: การเทียบข้อความตัวอย่างแบบตรงกันพิสูจน์ได้เฉพาะประโยคที่กำหนดไว้ คำถามที่สำนวนต่างออกไปถูกระบุ `NEEDS_HUMAN_SEMANTIC_REVIEW` ไม่ควรตีความว่าเป็นการคำนวณผิดหรือข้อเท็จจริงผิดทันที ต้องอ่าน refs/arguments/คำถามที่เก็บไว้ประกอบ ส่วนเกณฑ์ยอด จำนวนแถว การจัดซ้ำ และการส่งต่อเจ้าหน้าที่ตรวจแยกอย่างเป็นโครงสร้าง
